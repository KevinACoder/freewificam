## rtos-no-supplicant

- **Area:** rtos
- **Affected:** every RTOS wireless image (`wlan-*`, `rtl8xxxu-*`, `iwlwifi-*`, `rtw89-*`)
- **Status:** expected
- **Severity:** major
- **First seen:** 0.0.2

**Symptom.** The RTOS images associate with open access points only. Against a
WPA2 network there is no handshake: no supplicant is carried in this repository.

**Impact.** Encrypted networks cannot be used from an RTOS image. The Linux
module line is unaffected, because there the host's own supplicant drives the
interface.

**Workaround.** Use an open access point, or the Linux module line with a
supplicant.

**How it was observed.** Every RTOS board arm in this release used an open
access point; the radio and the driver associate and carry data, and no EAPOL
frame is produced because no application asks for one.

**Related.** `README.md` (lines), `tests/board/rtos/configs/`.

## iwl7260-uplink-rate

- **Area:** iwlwifi
- **Affected:** `iwlwifi-7260-sjd`, both kernels
- **Status:** open
- **Severity:** major
- **First seen:** 0.0.2

**Symptom.** The uplink is pinned near 0.3 Mbit/s. The access point reports a
transmit rate of 1.0 Mbit/s for this station, against 65-72 Mbit/s for the same
card under Linux. The downlink is about 10 Mbit/s.

**Impact.** The line is usable for control traffic and small transfers only.

**Workaround.** none.

**How it was observed.** 30 s TCP per direction, both kernels, two arms each,
2026-10-26: downlink 9.7-10.4 Mbit/s, uplink 0.26-0.38 Mbit/s; the same card
under Linux on the same access point measured 51.3-52.1 down and 33.1 up.
The access point's station table was read after every arm.

**Related.** `components/net80211/` (rate adaptation), `ports/pcie/`.

## iwl7260-join-rx-freeze

- **Area:** iwlwifi
- **Affected:** `iwlwifi-7260-sjd`, FreeRTOS
- **Status:** under investigation
- **Severity:** major
- **First seen:** 0.0.2

**Symptom.** In roughly one arm in four, the open join fails: the authentication
frame is sent (and usually acknowledged), then the device stops delivering
received frames within about half a second, and the interrupt line stops too.
The run ends with the association timing out.

**Impact.** A boot can fail to join even though the radio and the stack are
healthy; a power cycle recovers it.

**Workaround.** Power-cycle the board and repeat the boot.

**How it was observed.** 12 instrumented FreeRTOS arms, 3 failures, 2026-10-26.
In the failing arms the transmitted authentication frame is byte-identical to
the passing arms', the kernel's work queue is idle and no lock is held; the
receive count freezes before the interrupt count does. ThreadX did not
reproduce it in the arms run.

**Related.** `components/linuxkpi/rtos/pci/`, `tests/board/rtos/app/cases/iwl7260_join.c`.

## iwl7260-ko-tcp

- **Area:** iwlwifi
- **Affected:** `DRIVER=iwlwifi` module
- **Status:** open
- **Severity:** major
- **First seen:** 0.0.2

**Symptom.** The module joins and answers ping, but an iperf3 transfer carries
0 bytes in both directions; the client ends with "unable to receive results".

**Impact.** The Linux module arm cannot move TCP traffic on this part.

**Workaround.** Use the RTOS image for data, or the Linux built-in driver.

**How it was observed.** Two clean boots, 2026-10-26: join reported state 4 and
ping 5/5; iperf3 0 bytes both directions while the peer saw short bursts.

**Related.** `tests/board/linux-ko/`, `components/linuxkpi/rtos/pci/`.

## iwl7260-ko-handshake

- **Area:** iwlwifi
- **Affected:** `DRIVER=iwlwifi` module, WPA2
- **Status:** not reproducible
- **Severity:** minor
- **First seen:** 0.0.2

**Symptom.** One WPA2 association failed at the four-way handshake: the first
data frame after the handshake was never delivered and the access point
deauthenticated the station.

**Impact.** It did not recur; it is recorded because a repeat would look
identical to a healthy run until the deauthentication.

**Workaround.** Reboot and re-run.

**How it was observed.** One failing arm on 2026-10-25; seven clean boots on
2026-10-26 with the same module and access point all completed the handshake.
A payload-level capture in one arm showed a transmit failure at the retry limit
followed by a successful frame, which is consistent with a dropped handshake
message rather than a missing transmit path.

**Related.** `tests/board/linux-ko/ports/netdev/wlan_wext.c`.

## rtl8xxxu-rtos-uplink

- **Area:** rtl8xxxu
- **Affected:** `rtl8xxxu-8188eu-*`, `rtl8xxxu-8723bu-*`
- **Status:** open
- **Severity:** major
- **First seen:** 0.0.2

**Symptom.** The uplink is far below the same card under Linux: 0.10-0.14
Mbit/s for the RTL8188EUS (Linux 13.0-13.5) and 2.8-4.9 Mbit/s for the
RTL8723BU (Linux 10.3-12.9). The access point reports a low transmit rate for
both.

**Impact.** Uploads are impractical on the 8188EUS image and slow on the
8723BU image.

**Workaround.** none.

**How it was observed.** 30 s iperf2 per direction, both kernels, 2/2 arms each,
2026-10-26 and 2026-10-27; the same cards under Linux on the same access point
in the same rounds.

**Related.** `components/net80211/` (rate adaptation), `third-party/cherryusb/`.

## rtl8xxxu-rtos-rx-delivery

- **Area:** rtl8xxxu
- **Affected:** `rtl8xxxu-8188eu-*`
- **Status:** under investigation
- **Severity:** major
- **First seen:** 0.0.2

**Symptom.** In a small fraction of boots the radio receives but the frames do
not reach the 802.11 stack: a scan returns an empty table, or a join times out
after the authentication frame was sent. Other boots are fine.

**Impact.** A boot has to be repeated; no workaround beyond that is known.

**Workaround.** Reboot and repeat the arm.

**How it was observed.** 2 of 13 instrumented boots during the 8188EUS round,
2026-10-26. In the failing boots the USB adapter counted received transfers
while the bridge counted none. A later boundary-counter image did not reproduce
it on demand.

**Related.** `components/linuxkpi/rtos/usb/`, `components/net80211/ports/bridge/`.

## rtl8xxxu-rtos-scan-channels

- **Area:** rtl8xxxu
- **Affected:** `rtl8xxxu-8723bu-*`
- **Status:** workaround available
- **Severity:** minor
- **First seen:** 0.0.2

**Symptom.** A scan occasionally comes back without the access point that is
known to be present, in one boot out of a few. The same image finds it on the
next boot.

**Impact.** An arm fails to join because the access point never appears in the
table, which looks like a radio fault until the table is read.

**Workaround.** Re-run the scan (the case retries), or reboot.

**How it was observed.** Five first attempts across the 8723BU ladder round
failed this way (2026-10-27); every repeat passed, and the access point's own
beacon was visible on a second radio in the same window.

**Related.** `tests/board/rtos/app/cases/rtl8xxxu_scan.c`.

## rtl8xxxu-8723bu-composite

- **Area:** rtl8xxxu
- **Affected:** `rtl8xxxu-8723bu-*`, module
- **Status:** expected
- **Severity:** informational
- **First seen:** 0.0.2

**Symptom.** The RTL8723BU is a three-interface composite device: two Bluetooth
interfaces (no class driver) and the vendor-specific WiFi function on interface
2. The WiFi function is claimed and driven; the Bluetooth half is not.

**Impact.** The part's Bluetooth side is not supported by this repository.

**Workaround.** none; use the WiFi function only.

**How it was observed.** The discovery arm on 2026-10-27 enumerated all three
interfaces and the driver claimed interface 2; the two Bluetooth interfaces are
skipped by the class matcher.

**Related.** `tests/board/rtos/configs/rtl8xxxu-8723bu-*.mk`.

## linux-ko-reload

- **Area:** rtl8xxxu
- **Affected:** `DRIVER=rtl8xxxu` module
- **Status:** under investigation
- **Severity:** minor
- **First seen:** 0.0.2

**Symptom.** After the first unload and reload of the module on a clean boot,
the data path can be broken while the scan still works (ping fails, no error is
logged). A second reload fixes it.

**Impact.** Development and test loops that reload the module have to do it
twice.

**Workaround.** Reload once more, or reboot.

**How it was observed.** RTL8723BU, 2026-10-26: the first reload after a cold
boot carried 0 of 10 pings while a scan found 24 of 25 access points; the second
and third reloads passed. The driver bytes were the same in every arm.

**Related.** `tests/board/linux-ko/`, `wireless-drivers/rtl8xxxu/ports/`.

## rtw89-first-join

- **Area:** rtw89
- **Affected:** `DRIVER=rtw89` module, `rtw89-8851bu-*`
- **Status:** open
- **Severity:** major
- **First seen:** 0.0.2

**Symptom.** The first join after the firmware has loaded is intermittent, and
the link is poor when it does come up: the downlink is far below the uplink.
Received frames can stop after a scan.

**Impact.** The line is suitable for bringing the part up and for experiments,
not for data.

**Workaround.** Retry the join; reboot if the receive path stops.

**How it was observed.** The Linux module line reached a WPA2 association on
2/2 clean boots with the handshake complete (ping 20/19, iperf3 uplink 90.4 /
88.8 Mbit/s, downlink 1.68 / 1.55), while the RTOS arms measured bring-up,
scan, join and 20 KiB data 2/2. Earlier arms on both builds showed the
intermittent first join.

**Related.** `components/net80211/`, `wireless-drivers/rtw89/ports/`.

## rtl8189ftv-rtos-downlink

- **Area:** rtl8189fs
- **Affected:** `wlan-delivery`, both kernels
- **Status:** open
- **Severity:** major
- **First seen:** 0.0.2

**Symptom.** A 30 s TCP downlink can stop transferring while the interface
stays up: the receive count freezes and no error is logged. On FreeRTOS the
stop happened after about 1 MB in both arms. The same 30 s transfer in the
Linux reference build also stalls, at about 15-16 s, so the stall is not
specific to the RTOS image.

**Impact.** A sustained download cannot be relied on for this part.

**Workaround.** Reconnect; there is no in-band recovery.

**How it was observed.** 30 s TCP downlink, two arms per kernel, 2026-10-25:
ThreadX 7.70 / 7.55 Mbit/s with no stall; FreeRTOS stopped after 0.94 / 1.30 MB.
The Linux reference build, same access point and window, stalled at 15-16 s
with 73.8 / 74.6 MB carried.

**Related.** `wireless-drivers/rtl8189fs/`, `components/net80211/ports/bridge/`.

## rtos-throughput-gap

- **Area:** rtos
- **Affected:** every RTOS wireless image
- **Status:** open
- **Severity:** major
- **First seen:** 0.0.2

**Symptom.** Every RTOS line is below the same card under Linux on the same
board and access point. Measured ratios for this release:

| Line | Direction | This project / Linux |
|---|---|---|
| RTL8188EUS | downlink | 10.1-12.0 / 19.0-20.8 Mbit/s (about 0.5-0.6) |
| RTL8188EUS | uplink | 0.11 / 13.0-13.5 Mbit/s |
| RTL8723BU | downlink | 2.06-13.58 / 29.6-36.9 Mbit/s (about 0.3-0.5) |
| RTL8723BU | uplink | 2.81-4.94 / 10.3-12.9 Mbit/s (about 0.3-0.5) |
| AC 7260 | downlink | 9.7-10.4 / 51.3-52.1 Mbit/s (about 0.19) |
| AC 7260 | uplink | 0.26-0.38 / 33.1 Mbit/s |

**Impact.** The RTOS images are usable for control and modest data, not for
high-rate streaming.

**Workaround.** none; the gap is the subject of the line-specific entries above
and of future work.

**How it was observed.** 30 s iperf2 per direction, both kernels, 2/2 arms per
line, with the same access point as the Linux reference arms (2026-10-25 to
2026-10-27). The numbers are recorded, not gated.

**Related.** the line-specific entries in this file.

## rtos-feature-gaps

- **Area:** rtos
- **Affected:** every RTOS image
- **Status:** expected
- **Severity:** informational
- **First seen:** 0.0.2

**Symptom.** The RTOS images have no power save, no 40 MHz/HT operation, and no
access-point mode measured in this release. All hardware results come from one
board, and no long unattended run has been demonstrated on any line.

**Impact.** These are scope statements, not defects of a shipped path: a mode
that is not listed as measured in the release notes is not supported by this
release.

**Workaround.** none.

**How it was observed.** The profiles and the release notes define the scope;
the rounds behind the notes ran on one board with 20 MHz open access points.

**Related.** `docs/RELEASE-NOTES-0.0.2.md`.

## uvc-camera-wedge

- **Area:** camera
- **Affected:** `uvc`
- **Status:** workaround available
- **Severity:** minor
- **First seen:** 0.0.2

**Symptom.** A stream stop that takes this camera out of its streaming setting
can leave it refusing the video-streaming class requests for the rest of the
boot. The recovery sequences measured so far are not reproducible.

**Impact.** A camera that is stopped and reopened can stay unusable until the
board is power-cycled.

**Workaround.** The application half never closes the camera: it opens it once
and leaves it open, and the stream engine's stop leaves a caller-owned camera
open, so a later start issues no class requests at all.

**How it was observed.** The reference camera round recorded the behaviour on
this camera model; this release's application half is built around the
workaround, and the four board cases never close the camera.

**Related.** `ports/cherryusb/class/uvc_app.c`, `third-party/cherryusb/class/video/usbh_uvc_stream.c`.

## uvc-single-camera

- **Area:** camera
- **Affected:** `uvc`
- **Status:** expected
- **Severity:** informational
- **First seen:** 0.0.2

**Symptom.** The camera line is measured with one model: a Logitech Pro 9000
(`046d:0990`), 640x480 MJPEG, alternate setting 4. Other models, resolutions,
formats, concurrent cameras and hot-plug are untested. No long unattended run
has been demonstrated.

**Impact.** A scope statement: another camera may work, but this release does
not claim it.

**Workaround.** none.

**How it was observed.** Four clean boots, two per kernel, on the reference
board with that camera on its first USB2 root.

**Related.** `tests/board/rtos/configs/uvc.mk`, `docs/RELEASE-NOTES-0.0.2.md`.
