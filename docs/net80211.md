# The wireless core

The wireless path is the point of this project: a portable 802.11 stack that an
RTOS can adopt, with the Linux drivers running on top of it unchanged.

## Layers

```
  third-party/{rtl8xxxu, rtw88, rtw89}   Linux SoftMAC drivers, verbatim
                 |
  ports/net80211/bridge/                 the mac80211/cfg80211-shaped contract
                 |
  components/net80211/                   the 802.11 core, verbatim
                 |
  ports/net80211/{osal, net, compat}/    the OS/bus/net port layer
                 |
  os/cmsis2/                             CMSIS-RTOS2, over ThreadX or FreeRTOS
```

- **The core** (`components/net80211/`) is a verbatim import of a portable
  net80211 (NetBSD shape) with its own per-file licenses. It is not edited: the
  import is byte-fixed, and the record of it is `PROVENANCE.md` /
  `DIVERGENCES.md`.
- **The port layer** (`ports/net80211/`) is first-party glue and the only place
  the core meets this system. It is one implementation for both kernels: the
  OS adaptation (osal), the mbuf/ifnet presentation, and the compatibility
  shims the core expects. It calls the kernel only through CMSIS-RTOS2.
- **The bridge** (`ports/net80211/bridge/`) presents the driver-facing contract
  in the shape the Linux drivers expect: the mac80211/cfg80211 operations,
  the receive path, the vif/link/station bookkeeping and the scan/join
  lifecycle. A Linux SoftMAC driver compiled against this sees the interface it
  was written for.
- **The drivers** (`third-party/rtl8xxxu`, `rtw88`, `rtw89`) are verbatim
  extractions from Linux, pinned as submodules, with zero local patches.

## The authority rule

The core is the authority, and the driver aligns to it. The bridge presents the
contract the driver was written against; it does not relax or lengthen that
contract to accommodate a particular chip. Where a chip needs something the
interface normally supplies, the fix is on the driver side of the seam: give
the driver the state the interface promises (the vif address, the BSSID, the
channel, the callback serialisation) and let the chip's own filtering and state
machine work.

The practical test when reviewing a change: which side does it land on? A
change on the core or on the bridge contract is the wrong side and is sent
back; a chip-specific difference is absorbed in the driver or the interface
layer.

## What is ported

The drivers are ported as their own translation units against a first-party
interface face under `components/linuxkpi/`. The interface declarations are
first-party (a transcription of the Linux API shapes the drivers use, sized to
each driver's compile closure); the driver bytes are untouched. The build gate
for each line compiles the driver's translation units for the target and
checks the interface against the driver's own references, so an interface
gap shows up on the host before a board is involved.
